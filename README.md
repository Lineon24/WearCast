# WearCast ☀️

관심 지역의 날씨를 등록해두고, AI 챗봇에게 "오늘 뭐 입지?", "우산 챙겨야 돼?" 같은 걸 물어볼 수 있는
나만의 맞춤 날씨 대시보드입니다. Vue 3 + Pinia + Vue Router + Element Plus로 만들었습니다.

## 주요 기능

### 📋 날씨 대시보드
- 도시 이름 검색 또는 📍 내 위치(GPS)로 지역 카드 추가
- 기본 제공 지역(서울/수원/부산/안산/판교) + 내가 추가한 지역을 함께 표시
- 카드를 누르면 즐겨찾기(★) 등록/해제
- 카드 삭제 시 확인창을 거쳐 안전하게 제거 (기본 지역은 실제로는 "숨김" 처리)
- 한글 입력 즉시 반영되는 실시간 지역 검색/필터링
- 섭씨(°C) / 화씨(°F) 단위 전환

### 📊 상세 날씨 정보
- 실시간 기온 · 습도 · 풍속 · 공기질(PM2.5/PM10)
- 강수확률 · 강수량(mm) · 자외선 지수 게이지
- 24시간(3시간 간격) 및 5일 예보

### ⭐ 즐겨찾기
- 즐겨찾기한 지역만 모아보는 별도 페이지

### 🤖 날씨 챗봇
- 지역을 선택하면 그 지역의 실제 날씨 데이터를 근거로 답변
- OpenAI API 기반, 답변이 실시간 스트리밍(타이핑 효과)으로 출력
- 날씨/옷차림/우산 관련 질문에만 답하고, 무관한 전문 지식 요청은 정중히 거절 (가벼운 인사는 허용)
- 대화 기록은 지역별로 분리되어 저장되고, 다른 페이지를 오가도 유지됨

### 🎨 디자인
- Element Plus 컴포넌트 기반 UI, 라벤더/페리윙클 블루 테마로 전체 재구성
- 모바일 ~ 데스크톱까지 깨지지 않는 반응형 레이아웃

## 기술 스택

| 구분 | 사용 기술 |
|---|---|
| 프레임워크 | Vue 3 (`<script setup>`) |
| 상태 관리 | Pinia |
| 라우팅 | Vue Router |
| UI 컴포넌트 | Element Plus |
| 백엔드(챗봇 프록시) | Express(로컬 dev) / Vercel 서버리스 함수(Edge Runtime, 배포) |
| 날씨 데이터 | OpenWeatherMap API, Open-Meteo(자외선) |
| AI 챗봇 | OpenAI API (`gpt-4o-mini`) |
| 빌드 도구 | Vite |

## 시작하기

```bash
npm install
cp .env.example .env.local   # 아래 값을 실제 키로 채워주세요
npm run dev                  # 프런트엔드(5173) + 백엔드 프록시(8787) 동시 실행
```

`.env.local`에 필요한 값:

```bash
OPENAI_API_KEY=sk-proj-...          # 챗봇용, 서버 전용(클라이언트에 노출 안 됨)
OPENWEATHER_API_KEY=...             # 날씨 데이터용, 서버 전용(클라이언트에 노출 안 됨)
SERVER_PORT=8787                    # 선택, 로컬 프록시 서버 포트
```

```bash
npm run lint    # ESLint(+ oxlint) 검사
npm run build   # 프로덕션 빌드 (dist/ 생성)
npm run preview # 빌드 결과 로컬에서 미리보기
```

## 배포 (Vercel)

1. GitHub에 저장소를 올린 뒤 Vercel에서 Import
2. Vercel 프로젝트 Settings → Environment Variables에 `OPENAI_API_KEY`, `OPENWEATHER_API_KEY` 등록
   (둘 다 `VITE_` 접두사가 없는 서버 전용 값이라 Type을 Secret으로 둘 수 있습니다)
3. 배포 (Vite 프레임워크 자동 감지, `api/chat.js`·`api/weather.js`는 Vercel이 자동으로 서버리스 함수로 인식)

## 버전별 히스토리 & 트러블슈팅

개발하면서 실제로 겪었던 문제들과 해결 과정, 그리고 그 과정에서 느낀 점/배운 점을 버전별로 정리했습니다.

### 🏷️ v0.0.0 — 첫 버전

#### 1. 삭제한 기본 지역을 다시 추가할 수 없던 버그
기본 제공 지역을 삭제하면 `removedDefaultCityIds`에 추가해 목록에서만 숨기는 방식인데,
중복 체크 로직(`isDuplicateLocation`)이 이 숨김 목록을 고려하지 않고 원본 데이터와 그대로 비교해서
"삭제한 지역을 다시 검색해서 추가"하면 항상 "이미 등록된 도시"로 막혀버렸습니다.
→ 중복 체크 시 숨김 처리된 지역을 먼저 걸러내도록 수정.
> 💡 **느낀점/배운점**: "삭제"라는 말을 쓴다고 다 같은 삭제가 아니었습니다. 실제로 데이터를
> 지우는 건지, 화면에서만 숨기는 건지를 구현하기 전에 먼저 정의해뒀어야 다른 로직(중복 체크)이
> 헷갈리지 않는다는 걸 배웠습니다.

#### 2. 즐겨찾기 페이지에 내가 추가한 지역이 안 뜨던 버그
즐겨찾기 대상을 걸러낼 때 `weatherMockData`(기본 지역)만 보고 있어서, 검색으로 추가한 지역을
즐겨찾기해도 즐겨찾기 페이지에는 나타나지 않았습니다.
→ `customCitiesStore.cities`도 함께 합쳐서 걸러주도록 수정 (삭제된 기본 지역도 함께 제외).
> 💡 **느낀점/배운점**: 데이터 출처가 두 곳(기본 목록 + 내가 추가한 목록)으로 나뉘면, 한쪽
> 화면만 보고 "됐다"고 넘어가면 다른 화면에서 꼭 빠뜨린 부분이 드러난다는 걸 배웠습니다.

#### 3. 한글 IME + Enter 키로 발생한 버그들
- **미완성 텍스트로 검색/전송되는 문제**: 한글은 자모를 조합해서 완성하는데, 조합 중에 Enter를 누르면
  완성되기 전 값으로 `keyup.enter`가 먼저 발동하는 경우가 있었습니다.
  → `event.isComposing` / `event.keyCode === 229`를 체크해서 조합 중 Enter는 무시하도록 처리.
- **검색이 겹쳐서 두 번 실행되는 문제**: 위 이슈와 맞물려 검색 요청이 중복 실행되면서
  "방금 추가했는데 이미 있다"고 나오는 혼란스러운 버그로 이어졌습니다.
  → 요청이 진행 중이면(`isLoading`) 재실행하지 않도록 가드 추가.
> 💡 **느낀점/배운점**: 한글 입력은 "완성되는 순간"이 따로 있다는 걸 눈으로 직접 버그를
> 겪고 나서야 체감했습니다. 다국어(특히 조합형 문자) 입력을 다룰 땐 영어 기준으로만 테스트하면
> 절대 못 잡는 버그가 있다는 걸 배웠습니다.

#### 4. 검색이 "한 글자씩 밀려서" 반영되던 문제
Element Plus `el-input`은 한글 조합 중에는 `input`/`update:modelValue` 이벤트를 내보내지 않고
조합이 끝나야(`compositionend`) 값을 전달하도록 설계돼 있습니다. 그래서 실시간 검색 필터링이
한 글자(정확히는 한 음절) 늦게 반영되는 것처럼 보였습니다.
→ el-input 내부의 진짜 네이티브 `<input>`에 직접 이벤트 리스너를 붙여서, 조합 중에도
바로바로 필터링되도록 우회 처리.
> 💡 **느낀점/배운점**: 라이브러리 컴포넌트가 "왜 이렇게 동작하지?" 싶을 땐 대부분 나름의
> 설계 이유(여기선 조합 중 값 튐 방지)가 있다는 걸 알게 됐습니다. 무작정 우회하기 전에
> 왜 그렇게 만들어졌는지 이해하는 게 먼저라는 걸 배웠습니다.

#### 5. 검색창에서 backspace/빠른 타이핑 시 값이 씹히던 문제
위 4번을 고치는 과정에서 `:model-value`(부모 상태)를 다시 입력창에 흘려보내는 구조를 썼는데,
타이핑 속도와 "부모로 갔다가 돌아오는" 비동기 흐름이 서로 경쟁하면서 커서 위치가 튀거나
값이 예상과 다르게 잘리는 문제가 있었습니다.
→ 화면에 보이는 값은 컴포넌트 내부 `ref`(진짜 `v-model`)만 신뢰하고, 부모로는 필터링 알림만
편도로 보내는 구조로 정리해서 해결.
> 💡 **느낀점/배운점**: "부모 상태 → 자식 → 다시 부모"처럼 값을 왕복시키는 구조는 타이핑처럼
> 빠르게 반복되는 입력과 함께 있으면 타이밍 경쟁이 생기기 쉽다는 걸 배웠습니다. 화면에 보이는
> 값의 "진짜 주인"은 하나로 정해두고, 나머지는 편도 알림만 보내는 편이 훨씬 안전했습니다.

#### 6. 챗봇이 정상적인 날씨 질문까지 거절하던 문제
처음엔 "날씨 질문에만 답하고 나머지는 거절"이라는 규칙만 대충 넣었더니, 예시로 든 질문 패턴과
정확히 안 겹친다는 이유로 "이번주 날씨 어때?" 같은 명백한 질문까지 거절하는 과잉 거절이 발생했습니다.
→ 규칙을 "1) 날씨 질문 2) 가벼운 일상 대화 3) 전문 지식/작업 요청"으로 나누고,
애매한 경우엔 거절보다 답변 쪽으로 기울도록 프롬프트를 다시 작성.
> 💡 **느낀점/배운점**: 프롬프트도 코드처럼 "예시 몇 개"가 아니라 "카테고리/기준"으로 규칙을
> 세워야 한다는 걸 배웠습니다. 예시만 나열하면 모델이 그 표현과의 문자 그대로의 유사도에
> 기대게 되어, 의도는 같지만 표현만 다른 입력에 취약해집니다.

#### 7. 채팅창 자동 스크롤 타이밍 문제
메시지를 보내면 맨 아래로 스크롤하는 로직을 `nextTick` 안에서 처리했는데, DOM이 실제로
갱신되기 전에 스크롤이 실행돼서 씹히는 경우가 있었습니다.
→ `watch(..., { flush: 'post' })`로 바꿔서 DOM이 실제로 갱신된 뒤에 스크롤이 실행되도록 보장.
(카카오톡처럼 메시지를 보내면 무조건 맨 아래로, AI가 답변 중일 땐 이미 맨 아래에 있을 때만 따라가도록 처리)
> 💡 **느낀점/배운점**: `nextTick`만으로 타이밍이 항상 보장되는 게 아니라는 걸 배웠습니다.
> "DOM이 실제로 갱신된 뒤"가 중요한 로직이라면 `flush: 'post'`처럼 그 보장을 명시적으로
> 요구하는 옵션이 있는지 먼저 찾아보게 됐습니다.

#### 8. Element Plus 테마 커스터마이징 부작용
`--el-text-color-regular`를 흐린 회색으로 재정의했더니, 이 변수를 `el-input`이 "타이핑한 글자 색"으로도
그대로 써서 모든 입력창의 글자가 흐릿하게 보이는 버그가 있었습니다.
→ 진한 색으로 바꾸고 `--el-input-text-color`를 별도로 한 번 더 명시.
> 💡 **느낀점/배운점**: 컴포넌트 라이브러리의 CSS 변수 하나가 생각보다 여러 곳에서 재사용되고
> 있을 수 있다는 걸 배웠습니다. 변수 하나를 바꿀 땐 "이 변수를 또 어디서 쓰고 있는지" 한 번은
> 확인하는 습관이 필요합니다.

#### 9. 네비게이션 바 레이아웃 이슈
- 로고/메뉴를 위아래로 나눠(column) 배치했더니 화면이 좁아지는 애매한 구간(약 450~560px)에서
  줄바꿈이 되며 레이아웃이 깨졌습니다. → 한 줄(row) + `nowrap`으로 바꾸고, 로고/스위치는
  `flex-shrink: 0`으로 고정.
- 메뉴 영역에 `flex: 1`을 줬더니 배경(알약 모양)이 남는 공간을 억지로 채우며 늘어나서
  단위 전환 스위치와의 사이에 어색한 빈 공간이 생겼습니다. → `flex: 0 1 auto`로 수정.
- 라벨 글자 수가 달라서("소개" 2글자 vs "대시보드" 4글자) 메뉴 버튼 폭이 들쭉날쭉해 간격이
  고르지 않아 보였습니다. → `min-width`로 폭을 맞추고, 좁은 화면에서 라벨이 안 잘리도록 패딩도 같이 조정.
- 단위 전환 스위치가 기본 크기로는 옆 네비게이션 메뉴(높이 34px)보다 훨씬 작아(20px) 보였습니다.
  → `size="large"`로 높이를 맞춤.
> 💡 **느낀점/배운점**: 반응형 레이아웃은 아주 큰 화면/작은 화면만 보고 끝내면 안 되고, 그
> "애매한 중간 폭 구간"에서 실제로 어떻게 깨지는지 창 크기를 직접 늘렸다 줄였다 하며 확인해야
> 한다는 걸 배웠습니다. 그리고 "실제로 재봤을 때 문제없다"와 "눈으로 봤을 때 고르게 느껴진다"는
> 다른 얘기라, 결국 사람 눈에 자연스러운지가 더 중요할 때가 있다는 것도 알게 됐습니다.

#### 10. 아이콘을 이모지로 썼다가 톤이 흐트러졌던 문제
처음엔 아이콘을 이모지(📋ℹ️⭐🤖)로 썼는데, 브라우저/OS마다 이모지 색·굵기가 제각각이라

> 아이콘 라이브러리를 쓰는 게 낫습니다.

#### 11. API 키가 소스 코드에 하드코딩되어 있던 문제
개발 초반에는 OpenWeatherMap API 키가 `src/api/weather.js`에 문자열로 그대로 박혀 있었습니다.
→ `.env.local`(`VITE_OPENWEATHER_API_KEY`)로 옮기고 `.gitignore`(`*.local`)로 Git에는 올라가지 않도록 처리.
챗봇(OpenAI) 키는 처음부터 프런트엔드가 아닌 백엔드 프록시(Express/Vercel 서버리스 함수)에서만
사용하도록 설계해서 브라우저에 전혀 노출되지 않습니다.
> 💡 **느낀점/배운점**: "어차피 브라우저에서 다 보이니 상관없다"와 "git 이력에 영구히 남는다"는

### 🏷️ v0.0.1 — 배포 SDK문제 해결

#### 12. Vercel 배포 시 챗봇 스트리밍이 안 되던 문제
Vercel의 기본 Node.js 서버리스 함수는 응답을 스트리밍하지 않고 완료된 뒤 한 번에 반환합니다.
로컬 Express 프록시는 청크 단위로 바로바로 내려줘서 개발 중엔 문제를 못 느꼈습니다.
→ `api/chat.js`를 Edge Runtime(`export const config = { runtime: 'edge' }`)으로 전환해서
실시간 타이핑 효과가 배포 환경에서도 동일하게 동작하도록 수정.
> 💡 **느낀점/배운점**: "로컬에서 스트리밍이 잘 되니 배포해도 똑같겠지"라는 가정이 틀렸습니다.
> 서버리스 런타임마다 응답을 내려주는 방식(버퍼링 여부) 자체가 다를 수 있다는 걸 배웠고,
> 그 뒤로는 스트리밍/실시간성이 중요한 기능은 배포 환경에서 꼭 한 번 직접 확인하게 됐습니다.

#### 13. Edge Runtime에서 openai SDK가 배포 자체를 실패시키던 문제
위 12번대로 Edge Runtime으로 바꾸고 나니, 이번엔 Vercel 배포 자체가
`The Edge Function "api/chat" is referencing unsupported modules: - openai: #x509-transport-state`
에러로 실패했습니다. `openai` npm SDK가 내부적으로 Edge Runtime이 지원하지 않는
Node 전용 모듈(TLS 관련)을 참조하고 있었던 게 원인입니다.
→ SDK를 걷어내고, OpenAI REST API(`/v1/chat/completions`)를 `fetch`로 직접 호출한 뒤
응답으로 오는 SSE(Server-Sent Events) 스트림(`data: {...}\n\n`)을 직접 파싱해서
`delta.content`만 뽑아 내보내는 방식으로 교체. `fetch`/`ReadableStream`/`TextDecoder`는
전부 Edge Runtime이 지원하는 표준 웹 API라 이 문제를 완전히 피할 수 있었습니다.
(로컬 dev용 `server/index.js`는 일반 Node 프로세스라 SDK를 그대로 써도 문제없음)
> 💡 **느낀점/배운점**: npm SDK가 편하다고 해서 모든 런타임에서 그대로 동작하는 건 아니라는 걸
> 배웠습니다. Edge/Serverless처럼 제한된 런타임을 쓸 땐 SDK 뒤에 어떤 API가 감춰져 있는지
> 파악해두면, 문제가 생겼을 때 "표준 API로 직접 호출"하는 우회로가 있다는 걸 알게 됐습니다.

### 🏷️ v0.0.3 — 주소 문제 해결

#### 14. Vercel 배포 시 지역 카드 추가·내 위치 버튼이 작동하지 않던 문제
도시 검색(`GEO_DIRECT_URL`)과 역지오코딩(`GEO_REVERSE_URL`) 두 곳만 `http://`로 남아있었습니다
(다른 API 호출은 전부 `https://`). 로컬 dev 서버는 페이지 자체가 `http://localhost`라 문제가
드러나지 않았지만, Vercel에 `https://`로 배포하고 나니 "도시 이름으로 지역 추가"와
"📍 내 위치 버튼"(내부적으로 `reverseGeocode` 호출)이 조용히 실패했습니다. https 페이지에서
http로 나가는 요청은 브라우저가 **mixed content**로 판단해 차단하기 때문입니다.
→ 두 URL을 전부 `https://`로 수정.
> 💡 **느낀점/배운점**: 로컬에서 잘 되던 기능이 배포 후에만 깨진다면, 코드 로직보다 먼저
> "http vs https", "localhost vs 실제 도메인"처럼 환경 차이를 의심해봐야 한다는 걸 배웠습니다.
> 여러 URL 상수를 한 파일에 모아두고 하나씩 복사-수정하다 보면 프로토콜처럼 작은 부분을
> 놓치기 쉬우니, 전체를 한 번에 훑어보는 습관이 필요하다는 것도 느꼈습니다.

### 🏷️ v0.0.4 — 위치 중복 판정 개선

#### 15. GPS로 추가한 지역을 검색으로 또 추가할 수 있던 버그
중복 체크(`isDuplicateLocation`)가 위도/경도를 소수점 첫째 자리로 반올림해서 "같은 버킷이면
같은 지역"으로 판단했는데, 반올림 경계값 문제가 있었습니다. 예를 들어 위도 `37.549`와 `37.551`은

📍 내 위치 버튼은 GPS 실측 좌표를, 검색 추가는 지오코딩 DB의 대표 좌표를 쓰다 보니 같은 도시여도
값이 미세하게 달라 이 경계를 넘나드는 일이 실제로 발생했고, 결과적으로 같은 도시가 두 번
추가되는 버그로 이어졌습니다.
→ 반올림 버킷 비교 대신, 하버사인(Haversine) 공식으로 두 좌표 사이의 실제 거리(km)를 계산해서
5km 이내면 같은 지역으로 판단하도록 수정.
> 💡 **느낀점/배운점**: "적당히 반올림해서 묶으면 되겠지"라는 근사치 접근은 경계 근처에서
> 반드시 값이 튀는 지점이 생긴다는 걸 직접 겪고 나서야 체감했습니다. 위치처럼 연속적인 값을
> 다룰 땐 임의의 격자(버킷)로 나누기보다, 실제 거리·차이를 계산하는 쪽이 훨씬 안전하다는 걸
> 배웠습니다. 같은 종류의 버그(반올림/경계값)가 프로젝트 곳곳에서 반복될 수 있다는 것도
> 새삼 느꼈고, 앞으로 위치·시간처럼 "연속적인 값"을 비교하는 코드를 짤 땐 경계값을 한 번씩
> 의심해보는 습관을 들이기로 했습니다.

### 🏷️ v0.0.6 — 날씨 API 키 백엔드 프록시 전환

#### 17. OpenWeatherMap 키가 여전히 브라우저에 노출되던 문제
Vercel에 `VITE_OPENWEATHER_API_KEY`를 환경변수로 등록하려는데 "Environment variables with a

가려주지 않는 게 정상 동작이었고, 이 키는 처음부터 프런트엔드가 OpenWeatherMap을 직접 호출하는
구조라 브라우저 네트워크 탭에서도 그대로 보이고 있었습니다.
→ 챗봇(`api/chat.js`)과 동일한 방식으로 백엔드 프록시를 새로 만들었습니다. 날씨/대기질/예보/
지오코딩 요청 로직을 `api/_lib/weatherProxy.js` 공용 핸들러로 옮기고, `api/weather.js`(Vercel
서버리스 함수)와 `server/index.js`(로컬 Express)가 이 핸들러 하나를 그대로 같이 씁니다.
프런트엔드(`src/api/weather.js`)는 이제 OpenWeatherMap을 직접 호출하지 않고 `/api/weather`만
호출하며, 실제 키(`OPENWEATHER_API_KEY`, `VITE_` 접두사 없음)는 서버에만 존재합니다.
(자외선 지수를 가져오는 Open-Meteo는 키가 필요 없는 공개 API라 그대로 프런트에서 직접 호출)
> 💡 **느낀점/배운점**: "어차피 브라우저에서 다 보이니 상관없다"고 넘어갔던 걸 결국 나중에 다시
> 손보게 됐습니다. 처음부터 "이 키가 진짜 숨겨져야 하는가"를 정해두고 시작했다면 두 번 일하지
> 않았을 것 같습니다. 그리고 Vercel의 Secret/Config 에러 메시지처럼, 플랫폼이 주는 에러가
> 오히려 설계상 놓친 부분을 짚어줄 때가 있다는 것도 느꼈습니다. 마지막으로, 프록시 로직이
> Express(req.query/res.json)와 Vercel Node 함수(req.query/res.status().json())에서 거의
> 동일하게 동작한다는 걸 알고 나니, 두 곳에 로직을 중복해서 짜기보다 공용 핸들러 하나로
> 합치는 게 훨씬 유지보수하기 편하다는 것도 배웠습니다.

### 🏷️ v0.0.7 — 폰트 로딩 문제 해결

#### 18. Windows에서만 네비게이션 메뉴가 오른쪽으로 밀려 보이던 문제
Mac/모바일에서는 멀쩡한데 Windows에서만 헤더 네비게이션("챗봇" 등)이 살짝 오른쪽으로 쏠려 보인다는
제보를 받았습니다. `base.css`의 폰트 스택 맨 앞에 `'Pretendard Variable', Pretendard`를 지정해뒀지만,
실제로 이 폰트를 불러오는 `@font-face`나 CDN 링크가 프로젝트 어디에도 없었습니다. 브라우저 콘솔에서
`document.fonts`를 직접 찍어보니 로드된 폰트가 하나도 없었고, 그래서 항상 그 다음 순번인 OS 기본
폰트로 렌더링되고 있었던 겁니다. Mac/iOS는 `-apple-system`(+Apple SD Gothic Neo)으로 떨어지는데,
Windows는 `Inter`/`-apple-system`/`BlinkMacSystemFont`가 전부 존재하지 않는 폰트라 건너뛰고
`Segoe UI`+맑은 고딕으로 렌더링됩니다. 맑은 고딕이 애플 고딕보다 한글 글자폭이 넓다 보니, `min-width`/
`padding`을 픽셀 값으로 고정해둔 네비게이션 메뉴가 OS별로 다르게 밀려 보였던 것입니다.
→ `index.html`에 Pretendard 웹폰트(CDN)를 실제로 로드하도록 `<link>`를 추가했습니다. 이제 OS와
무관하게 항상 같은 폰트로 렌더링되어, 특정 OS만을 위해 레이아웃 수치를 따로 손보지 않아도 됩니다.
> 💡 **느낀점/배운점**: CSS에 폰트 이름만 적어놓고 실제로 불러오는 걸 깜빡하면, 에러도 안 뜨고
> 그냥 조용히 다음 폰트로 넘어가버려서 한참 동안 못 알아챌 수 있다는 걸 배웠습니다. `font-family`에
> 웹폰트를 적었다면 `document.fonts`로 실제 로드됐는지 한 번은 확인해보는 습관을 들여야겠다고
> 느꼈습니다. 그리고 이번 것처럼 "내 컴퓨터(Mac)에서는 멀쩡한데요"라는 버그는 십중팔구 플랫폼별로
> 다르게 동작하는 기본값(이번엔 시스템 폰트) 때문이라는 것도 다시 한번 체감했습니다. 레이아웃을
> 특정 폰트의 글자폭에 맞춰 픽셀 단위로 고정해두는 것 자체가 이런 문제에 취약하다는 것도 배웠고,
> 근본 원인(폰트 미로드)을 고치는 대신 레이아웃 수치만 OS별로 땜질했다면 나중에 폰트가 하나 더
> 바뀔 때마다 똑같은 문제를 반복했을 것 같습니다.

### 🏷️ v0.0.8 — 도시 검색 지명 충돌 문제 해결

#### 19. "안산" 검색하면 한국이 아니라 중국 안산(랴오닝성)이 뜨던 문제
경기도 안산시 날씨 카드가 실제로는 중국 랴오닝성 안산시(鞍山) 날씨를 가리키고 있다는 제보를
받았습니다. 원인을 API로 직접 재현해보니, OpenWeatherMap 지오코딩에 "안산"으로 검색하면
한국 경기도 안산시(country: KR)와 중국 랴오닝성 안산시(country: CN)가 둘 다 검색되는데, 공교롭게
중국 안산시의 `local_names.ko`도 똑같이 "안산시"였습니다(한자 鞍山의 한국어 발음이 우연히 같음).
그런데 검색 결과 순서가 이름 일치가 아니라 API 자체 순위(인구 등으로 추정)를 따르다 보니, 기존
코드가 요청하던 `limit:1`(최상위 결과 1개만)로는 엉뚱한 도시가 걸릴 수 있었습니다. `country=KR`로
필터링해봐도 "안산" 검색에 전혀 관련 없는 "양산시"가 최상위로 나오는 경우까지 확인해서, 국가
필터만으로는 부족하다고 판단했습니다.
→ 후보를 여러 개(`limit:10`) 받아온 뒤, 검색어와 실제로 이름이 일치하는 후보만 걸러내고 그중에서도
한국(KR)을 우선하도록 프런트엔드에서 직접 골라내는 `pickBestMatch` 함수를 추가했습니다
(`src/api/weather.js`). 브라우저에서 "안산"을 다시 검색해서, 이제 기존 경기도 안산시 카드와 같은
좌표로 판정돼 중복 추가가 막히는 것까지 직접 확인했습니다(수정 전이었다면 중국 안산은 ~800km
떨어져 있어 중복으로 안 잡히고 엉뚱한 카드가 새로 추가됐을 것입니다).
> 💡 **느낀점/배운점**: 외부 API의 "검색 결과 1등"을 무조건 믿으면 안 된다는 걸 배웠습니다.
> 특히 여러 나라에 걸쳐 이름이 같거나 비슷하게 로컬라이즈되는 지명(이번엔 한자 문화권 지명의
> 한국어 발음 충돌)은 흔히 생각하는 것보다 자주 부딪히는 문제라는 것도 알게 됐습니다. 그리고
> 이런 버그는 고치고 끝내는 게 아니라, "정말 고쳐졌는지"를 API 응답을 직접 눈으로 찍어보고
> (limit을 늘려서 후보들을 다 까본 것), 실제 화면에서 재현해서 확인하는 과정이 있어야
> 확신을 가질 수 있다는 것도 다시 느꼈습니다. 이번엔 마침 v0.0.4에서 고쳤던 위치 기반 중복 체크
> 로직(15번 항목)이 검증 도구 역할도 해줘서, 이전에 고친 기능이 다음 버그를 검증하는 데
> 도움이 되기도 한다는 걸 경험했습니다.

### 🏷️ v0.0.9 — 지역 카드 정렬 기능 추가

#### 20. 즐겨찾기·최근 추가 지역이 맨 위로 오도록 카드 정렬 개선
기존에는 카드 순서가 "기본 제공 지역(고정 순서) + 내가 추가한 지역(최신순)"으로만 정해져 있어서,
즐겨찾기한 지역이라도 목록 아래쪽에 묻혀 있으면 스크롤해서 찾아야 했습니다.
→ `customCities.js`의 `addCity`에 지역을 추가한 시각(`addedAt`)을 저장하고, `WeatherHomeView.vue`에
`sortedWeatherList`를 추가해서 ①즐겨찾기 여부(즐겨찾기 먼저) → ②추가 시각(최근 추가한 것 먼저) 순으로
정렬하도록 했습니다. 기본 제공 지역은 추가 시각이 없어서 가장 오래된 것으로 취급되지만, `Array#sort`가
안정 정렬이라 그 지역들끼리의 원래 순서(서울→수원→부산→안산→판교)는 그대로 유지됩니다. 브라우저에서
즐겨찾기 토글 + 새 지역 추가를 같이 해보면서, 즐겨찾기 카드가 맨 위로, 그다음 방금 추가한 카드가
그 아래로 오는 것까지 직접 확인했습니다.
> 💡 **느낀점/배운점**: 정렬 기준이 여러 개(즐겨찾기, 최근순)일 땐 "1순위가 같으면 2순위로 비교"하는
> 다단계 비교 함수로 짜는 게 각각 따로 필터링/재배치하는 것보다 훨씬 명확하다는 걸 다시 확인했습니다.
> 그리고 기본 제공 지역처럼 애초에 "추가 시각"이라는 개념 자체가 없는 데이터를 다룰 때, `undefined`를
> 그냥 두기보다 `?? 0`처럼 명시적인 기본값을 줘서 "가장 오래된 것으로 취급"이라는 의도를 코드에
> 드러내는 게 나중에 읽을 때 훨씬 이해하기 쉽다는 것도 느꼈습니다. 마지막으로 `Array#sort`가 안정
> 정렬이라는 걸 알고 있었기 때문에 "동점일 때 원래 순서를 믿고" 로직을 단순하게 짤 수 있었는데,
> 이런 언어/API의 기본 보장 사항을 알아두는 게 코드를 간결하게 만드는 데 실제로 도움이 된다는 걸
> 체감했습니다.
